# Experimental 0G bridge and verification tooling

For the normal router integration, configuration and acceptance behavior, start with the [0G integration guide](../../docs/0G_INTEGRATION_README.md). This directory contains optional research tooling; it is not required to run the normal router classifier. Local verification observations below are not a claim of complete live request-bound attestation.

This experimental bridge can be selected by an explicit gateway setting; it is disabled by default. It builds from a locally patched archive of the upstream 0G client at commit `c0e7d23f03adea19cbac36223bbeabe05cc8eaad`, whose local sidecar and SDK are unsupported beta interfaces. It invokes the upstream client core without opening a local HTTP listener and fixes the testnet/mainnet router and strict provider-verification flags in source. It reads a single request containing an API key and classifier JSON body from stdin, rejects unknown fields, streaming, missing verification and unexpected message shapes, and emits a JSON response to stdout only for HTTP 200 with a bounded, conservatively formatted `ZG-Res-Key`. Other responses fail without returning the upstream error body. The accepted key format has not yet been validated against a real service. Both pipes can contain private data; do not log or persist them.

For a reviewed checkout of that exact upstream commit, run `.venv/bin/python scripts/build_0g_bridge.py CHECKOUT_PATH GO_EXECUTABLE OUTPUT_PATH`. The helper verifies the commit and builds from a Git archive of that commit, so worktree modifications are excluded. It refuses to overwrite the destination and invokes Go with its local toolchain. The helper does not authenticate the checkout or dependencies, prove reproducibility, or audit the binary. Review the checkout, dependencies, build environment, binary and trust roots before use. Run the optional invalid-input smoke tests with `MEMORYSEAL_TEST_0G_BRIDGE` pointing at the binary. They do not send an inference request.

No trusted binary verification, live funded request, or independent validation of upstream attestation and response-binding behavior has been completed. Do not treat successful compilation or startup as proof of a verified inference. The bridge is not an acceptance result, and upstream changes require a fresh review.

Install the optional verifier dependency with `.venv/bin/pip install -e '.[bridge-verification]'`. Run the Go tests against a disposable patched archive with `.venv/bin/python -m scripts.test_0g_bridge CHECKOUT_PATH GO_EXECUTABLE`. The local fake-provider test decrypts and checks the original classifier messages, challenge and model, and covers response-signature verification and wrong-signer rejection through the shared handler. It uses a test provider's private key and does not exercise real provider attestation, onchain grounding or production bridge wiring. PyHPKE states that it has not been formally audited; review and protect this dependency and the build environment before use.

`memoryseal.bridge_runner` is an experimental subprocess boundary. It checks an operator-supplied SHA-256 digest before execution, passes one bounded JSON request over stdin, limits stdout and execution time, suppresses stderr, restricts inherited environment variables, and terminates the process group on completion or failure. It validates the response envelope but cannot establish that the binary performed the claimed checks. The operator must protect the executable and its parent directories from replacement: hashing a path before executing it is not an atomic integrity guarantee. The bridge runs with the gateway user's operating-system privileges and is not a sandbox. Its stdin and stdout contain sensitive data. This runner currently requires POSIX process-group and selector semantics.

`memoryseal.bridge_transport.BridgeTransport` adapts the runner to the classifier's HTTP interface for local experimentation. It only accepts the fixed HTTPS router and chat-completions endpoint for its configured network, requires private mode, the configured provider pin and disabled fallback, and passes the provider, signer and endpoint pins to the bridge. It does not promote a bridge response into an attestation claim. The gateway can instantiate this transport with explicit experimental configuration. Its output does not establish independent verification. Admission follows the current gateway acceptance policy; the bridge itself grants no exception.

The bridge sends the private trust-mode routing directive to the upstream handler. Local tests demonstrate that the handler forwards it; they do not prove the live router honors it. The upstream route resolver can replace a forwarded routing pin with a preview-selected candidate. The experimental build includes a pre-sealing check for that candidate; the Python transport now passes the same pins to the bridge, but the gateway can use it only when explicitly configured.

`pinned_resolver.go` is an experimental resolver wrapper for checking the first materialized provider's address, signer, and endpoint before the upstream core seals a request, and for refusing fallback candidates. Its tests use a fake resolver and include a core-client check that a mismatched candidate receives no request. The build helper injects a narrow resolver hook into the pinned upstream archive and the bridge supplies this wrapper with mandatory provider, signer and endpoint pins. The hook is a local modification to upstream code; a test exercises the bridge client builder and verifies a mismatched fake candidate receives no model request. A real routed inference and independent review remain necessary. Materializing a candidate may itself perform upstream control-plane requests. These tests do not establish attestation or live provider behavior.

Enable the experimental gateway path only with `MEMORYSEAL_ZERO_G_EXPERIMENTAL_BRIDGE=true`, an absolute `MEMORYSEAL_ZERO_G_BRIDGE_EXECUTABLE`, its lowercase SHA-256 in `MEMORYSEAL_ZERO_G_BRIDGE_SHA256`, and the API key, model and all three provider pins. It cannot be combined with the separate required gateway-connection attestation option; incomplete or conflicting configuration quarantines memories without invoking inference. The binary digest is checked on every invocation. Successful bridge output remains `unverified` and quarantined until real evidence and a reviewed verification policy support a stronger status.

Because all bridge results are currently quarantined, the research agent cannot read a newly written research memory in this mode. The full P0 demo therefore cannot pass with the experimental bridge as it stands. A verified release requires evidence-backed provider verification and a reviewed policy for accepting eligible results; do not override quarantine merely to make the demo pass.

The bridge now requires the upstream client's locally reported `X-Provider` to match the configured provider and returns that value to the Python transport, which checks the match again. Older bridge binaries that do not return this field are rejected and must be rebuilt and re-pinned. The dashboard labels the value as a bridge assertion; it is not independent evidence of provider attestation or response binding. Live behavior and the field's availability have not been verified.

To run the same isolated Go tests with the race detector, add `--race` to the `scripts.test_0g_bridge` command. This requires a Go toolchain and platform that support the detector. A passing race run does not establish live provider attestation or exhaust all possible concurrency issues.

The build also patches the pinned upstream buffered completion path to read at most 4 MiB plus one byte of the sealed provider response before rejecting an oversized body. The earlier bridge output limit applied only after upstream had read and decoded that body. The patch is checked against the exact expected source shape, and the test runner exercises both the read boundary and a fake oversized upstream response. This bound is specific to non-streaming completion responses; it is not a process memory limit or an audit of every upstream network response. Rebuild and re-pin any previously built bridge binary to include it.

The patched core exposes the signed hash text and signature only after its non-streaming verification succeeds; the one-request bridge emits them in its bounded response. Where the combined request and response binding artifacts are at most 200,000 bytes, it also emits the bridge-reported AAD and ciphertext. The Python transport independently checks the receipt's scheme and signer, recomputes the signed hashes over those supplied bytes, and rejects inconsistent supplied artifacts. It records only the check results, not the receipt or artifacts. AAD contains cleartext protocol metadata and the pipes also contain sensitive data; do not log them. Larger artifacts are omitted and yield no binding observation. Older binaries that reject the new challenge field fail closed and must be rebuilt. These hash checks alone do not establish that the artifacts were transmitted on the wire, that they encode the original plaintext, or that provider attestation passed; the separate request-material check described below adds a plaintext comparison when its inputs are available. The bridge result stays unverified and quarantined.

The Python transport generates a fresh 256-bit random challenge in the standard `user` field for every bridge request. This value is visible to the router and provider and must not contain user identity or private data. When binding artifacts are supplied, the gateway requires the challenge in the signed request AAD, rejects duplicate JSON keys, and rejects a `user` field listed as unbound or sealed. This detects reuse of an older receipt across attempts when artifacts are available, but a bridge can still submit different plaintext under the same challenge; the check does not prove plaintext binding or attestation. Receipts without artifacts provide no challenge observation. Live provider compatibility with the added field has not been verified. Rebuild and re-pin the bridge before use.

The same post-response diagnostic requires the bridge-reported manifest to list `messages` as sealed and omit it from AAD. It cannot prevent a dishonest executable from having already sent plaintext or prove that unreported traffic was safe. The pinned-archive test runner exports a temporary synthetic receipt produced by its fake Go provider and checks its signature, binding and challenge using the Python verifier; a modified ciphertext must fail. The fixture contains synthetic keys and content and is removed with the temporary archive.

For newly checked artifacts, the Python diagnostic requires the signed AAD to contain the requested numeric temperature and model and excludes both from the sealed and unbound lists. The build now configures the upstream client to bind all request fields; upstream's default leaves `model` unbound for router rewriting ([upstream design](https://github.com/0gfoundation/0g-pc-e2ee/blob/c0e7d23f03adea19cbac36223bbeabe05cc8eaad/docs/design/request-envelope-and-integrity.md)). Rebuild and re-pin the bridge; an older bridge with unbound model artifacts is rejected. Live routers may rewrite model aliases, causing this mode to fail, and compatibility is unverified. Missing artifacts provide no model-binding observation. Signed ciphertext and these checks do not independently establish which model executed or that the bridge reported the actual wire traffic. Existing challenge observations on older records do not imply these checks occurred.

The pinned-archive local tests compare the two upstream sealing modes: changing the model still decrypts when it is unbound, while changing a bound model causes decryption to fail. These use local generated keys; they do not exercise the live production bridge wiring. An explicit accepted model identity and live compatibility remain to be established. Binding a request model does not prove the model actually executed or resolve plaintext binding and attestation.

The rebuilt bridge also returns the one-use response private key to its local gateway process when it supplies bounded receipt artifacts. After checking the signer, hashes and challenge, the gateway uses PyHPKE to open the reported response ciphertext and compares the decrypted choices with the bridge's response. It checks the key's public half against the signed request AAD and records only a boolean observation. The key and all pipe contents are sensitive: never log, persist, publish or share them. The bridge executable still sees both plaintext and key and is trusted; this check does not establish that the original request plaintext was sent, validate provider attestation, or establish actual model execution. Receipt artifacts or the key may be missing on older binaries or large responses; no response-choices observation is then made. The bridge remains quarantined even when all observations pass. Rebuild and re-pin the binary to enable this check, and restart the gateway with the optional dependency installed. The test fixture writes only synthetic keys and content to a temporary directory, which is removed after the test.

The response opener supports both base HPKE and 0G's optional response-binding PSK mode. It selects the mode from the signed request AAD's sealed-field list and derives the PSK from the ephemeral key as specified by the pinned upstream protocol. Local cross-language fixtures cover both modes and reject a mode downgrade and altered response. This response binding is separate from independently proving that the sealed request contains the intended classifier input; live compatibility and provider attestation remain unverified.

The rebuilt experimental bridge also passes the request's one-use HPKE seed, recipient public key and sealed-field plaintext to its local parent. After signature, ciphertext-hash and challenge checks, the gateway independently re-creates the HPKE ciphertext and compares the sealed messages with the original local classifier request. For PSK-mode responses it also checks the sealed `_bind` value against the response key. Only a boolean is recorded; the seed and plaintext can disclose the request and must never be logged, persisted, published or shared. This observes a signed ciphertext and bridge-supplied recipient key; it does not authenticate that key against a real provider quote, prove actual wire traffic, attest the provider or prove which model executed. Bounded artifacts may be absent; old binaries and large responses can therefore yield no observation. The Go capture is designed for this bridge's one-request process, not a concurrent multi-tenant upstream server. These observations do not make the inference independently verified; live behavior has not been verified. Rebuild and re-pin the bridge before using this observation.

An experimental Python adapter, `memoryseal.zero_g_provider_verifier.verify_provider_quote`, runs an operator-supplied `pcverify` in strict provider mode and extracts the quote-reported encryption key and signer only after a successful, unambiguous result. It bounds output and time, does not pass MemorySeal environment secrets, and does not print the verifier output. The configured RPC URL and endpoint are passed as process arguments and can be visible to other local processes; do not embed secrets in them. The binary, its baselines and trust roots, and the RPC are trust inputs. The adapter does not independently check the RPC chain ID, and a separate pass does not attest a particular request. Its optional gateway integration is described below; results remain quarantined.

The bridge and `BridgeTransport` accept an optional 32-byte lowercase hexadecimal recipient-key pin. When supplied, the bridge compares it to the resolved provider's encryption key before sealing, and Python requires the checked receipt's recipient key to match as well. A mismatch rejects the request, and a local fake-server test confirms no request was sent. Older bridge binaries reject the new field, so rebuild and re-pin the executable before using it. This pinning check does not itself authorize acceptance.

For experimental use, set `MEMORYSEAL_ZERO_G_PROVIDER_VERIFIER` to an operator-reviewed strict verifier executable, set `MEMORYSEAL_ZERO_G_PROVIDER_VERIFIER_SHA256` to its lowercase SHA-256 digest, and configure the registry RPC and provider pins. The gateway checks the registry and verifier result before invoking the bridge, then supplies the returned encryption key as the recipient pin. A failed verifier, digest mismatch, or invalid result prevents bridge invocation. Readiness checks configuration shape and executable presence; the digest is checked at invocation, and readiness does not check connectivity or verifier correctness. Protect the verifier executable and parent directories against replacement: hashing before execution is not atomic. The verifier, its baseline and trust roots, RPC, and bridge remain operator trust inputs; the verifier receives the RPC and endpoint as arguments, so do not embed credentials in those URLs. The recorded key-match flag is a local observation, not proof of live execution or actual wire traffic. Do not use this experimental path for private data until the complete trust and live verification path is established.
